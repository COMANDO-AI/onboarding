01El sistema

Trece repos, cuatro runtimes,
una sola firma

Esto no es un repo con un asistente. Son 13 repos, cuatro runtimes de agente y dos proveedores de modelo, con una sola persona que aprueba. El trabajo entra por una de tres lanes y todo lo que puede romper algo vuelve a la misma firma.

Tres hechos que ordenan todo lo demás

01
Un escritor activo por repo/branch
Dos agentes no escriben el mismo árbol. Lane 3 existe porque el worktree le da branch propia a Hermes sin tocar el lock de Lane 1.
02
El revisor nunca es del mismo proveedor
Claude revisando a Claude no es segunda opinión. Escribe OpenAI → revisa Anthropic, y al revés. Se verifica por packet, no por asignación fija.
03
El repo le gana a la memoria
Precedencia: repo docs → packet activo → memoria del agente → transcript. Si el chat y el archivo se contradicen, gana el archivo — y corregís el que perdió en la misma sesión.
02Con qué operás

Claude Code, primero

La herramienta principal

Claude Code

Todo lo demás es periferia. Corre en la terminal, en la extensión de VS Code, en la app de escritorio y en claude.ai/code. Acá se usa adentro de un repo por vez: abrís el repo, Claude lee su CLAUDE.md en el boot, y esa sesión es esa sesión.

Lo que tenés que entender, en el orden en que te va a hacer falta

01
CLAUDE.md
El archivo que se auto-carga al abrir el repo. Es la política de esa sesión. Cada repo tiene el suyo.
02
Contexto
La ventana es finita; las sesiones largas se resumen. Por eso el estado vive en archivos, no en el chat.
03
Skills
Procedimientos guardados en .claude/skills/. Se invocan con /nombre. Acá hay 14.
04
Subagentes
Tareas que corren aparte, en su propio contexto, y devuelven sólo la conclusión. Para búsquedas anchas y research.
05
Plan mode
Modo de sólo lectura donde se diseña antes de tocar nada. Se sale con aprobación explícita.
06
Permisos
Qué corre sin preguntar. git push pregunta siempre; leer un .env está prohibido.
07
MCP
Servidores que le dan herramientas externas: Notion, Figma, Gmail, Excalidraw.
08
Modelos y costo
Opus para razonar, Sonnet para construir, Haiku para volumen. Un agente público en Opus sin tope es dinero real.

03Cómo se mueve el trabajo

Tres lanes. Ninguna es degradada

Lane 1 · DirectaLane 2 · PacketLane 3 · Kanban
CuándoEl día a díaCuando el alcance hay que fijarlo por escritoCuando querés que se haga sin vos en el loop
EntradaAbrís el repoTelegram → Hermes Mainbin/task <repo> "título"
EscribeVos + Claude CodeClaude Codedev (Hermes, OpenAI)
DóndeEl árbol principalEl árbol principalSólo .worktrees/<id>
Revisa—Subagente reviewer / reviewer-openaireviewer-claude
SaleCommit (con aprobación)Packet cerrado + veredictoBranch esperando merge
CierraVosVosVos, a mano. Siempre.

Cómo elegís. Arrancá siempre por la 1. Un packet se gana su costo cuando el alcance, el riesgo o la continuidad necesitan estar escritos. El kanban es para trabajo delegado, en un repo registrado, donde el resultado correcto es una branch para mergear. Trabajo que arranca directo y resulta más grande deja un WORK_REPORT.md al final, o se gradúa a packet a mitad de camino.

El ritmo de una sesión

Abrir
  1. Abrir el repo en Claude Code
  2. Leer cadence/pulse.md — open, blocked, done
Trabajar
  1. Decir la intención de la sesión
  2. Trabajar — un repo por vez
Cerrar
  1. Correr upc
  2. pulse · decision_log · evolution_log · dashboard · commit

upc no es opcional. Si la sesión no se cierra, el próximo que abra el repo no sabe qué pasó.

04Qué te frena

Compuertas, no intenciones

Esto no es una lista de buenas prácticas. Son las compuertas del sistema.

Requieren aprobación explícita del principal

CompuertaPor qué
git push, deployPuede llegar a producción. skins-md y comando-ai.com deployan solo.
Commits, cuando el packet dice parar antesProtocolo, no enforcement. El harness ya no pregunta.
Cualquier secreto: leer, sincronizar, imprimirNunca entran a prompts, docs ni reportes.
Mergear o pushear una branch de Lane 3Siempre a mano. Es el punto del diseño.
Reasignar el writer lockCambiar quién escribe un repo es una decisión, no un ajuste.
Registrar un repo para Lane 3Le abre la puerta a un escritor autónomo.
Mutar un VPS, launchd, contenedoresInfra corriendo.
Comunicaciones externas: mail, DMs, posts, facturasSalen del estudio. Los drafts van a COMS/.
Escribir en context/identity/Es la identidad. No se toca.
Modificar C-OS.md fuera de un incremento de MarkEs el boot spec.
Onboardear un cliente nuevoCompromiso comercial.
Reglas duras, sin excepción

Los secretos nunca tocan el disco. 1Password es el único almacén; op run los inyecta en ejecución. connections/ documenta dónde vive una credencial, nunca el valor. Ese es el contrato de auth.

Un escritor activo por repo/branch. Si no está escrito en el registry, no escribís. Ningún perfil revisa su propio trabajo, ni el de su mismo proveedor.

Evidencia antes de aprobación. Código: git diff --stat y tests corridos con las fallas a la vista. Visual: screenshot, no "el build pasó". Ops: la ruta del reporte. Lo que falta se declara faltante. Nunca se dice hecho sin evidencia.

05Cómo se lee cualquier repo

Aprendés uno, los leés todos

Todos los repos de COMANDO tienen la misma forma: cuatro capas, con un flujo de datos que va de lo vivo a lo durable.

Dos ejes que no chocan: 4C dice dónde vive un archivo. AREA dice qué hace.

PiezaRegla
IDsKIND_AREA_ROLE. KIND ∈ {AG, WF, TL}. AREA ∈ {CORE, WEB, MKT, LAB, CANON}. El nombre del archivo es el ID.
FrontmatterTodo archivo operativo abre con YAML: status, owner, updated.
Prosakebab-case.md.
Charter vs OS layerCharter = CLAUDE.md + .claude/, el runtime, fijo. OS layer = el contenido 4C + C-OS.md, versionado por Mark.

Por qué esta forma. Un harness es la capa que decide qué ve un modelo y qué puede hacer. No se toca el modelo: se escribe el harness. Cada .md del repo es parte del harness. El Canon es el meta-harness — el harness que construye harnesses.

Estado del repo, hoy

C-OS.md dice Mark IV. El reencuadre a fábrica agéntica está acordado (decision_log, 2026-09-22) y sin escribir. El repo está a mitad de camino entre dos Marks. Escribir el Mark V es trabajo abierto.

06Qué vendemos

Un método, no horas

COMANDO es una fábrica agéntica: capacidades, agentes y sistemas operativos completos. Dos capas — A (thinktank) aguas arriba, B (servicios) aguas abajo; B mantiene viva a A. Dos caras: comando-ai.com (el AI OS productizado) y comando.live (el estudio creativo).

Los tiers, y dónde está el trabajo FDE

TierPrecioQué es¿Delivery embebido?

AI OS Build$14,000Un stack agéntico diseñado y deployadoSí

El Diagnostic está debajo de la línea a propósito: es el bootcamp — tres a cinco días con la data real del cliente, software funcionando al final, no demos. Es el instrumento de entrada. Vender el Diagnostic como delivery embebido es la forma más rápida de perder plata. Todo engagement arranca en una discovery call de 30 minutos; no hay checkout online.

07Tu rol

Forward Deployed Engineer

Todos acá trabajan como FDE. Es la descripción precisa de lo que ya se hace. El documento canónico de Palantir define el rol en una línea:

El foco de un Dev es "una capacidad, muchos clientes". El de un Delta es "un cliente, muchas capacidades".

Palantir · Dev versus Delta

Eso es exactamente la relación entre una instancia y el Canon. Tirás un camino rápido y sucio para un cliente; cuando el mismo camino se tiró tres veces, se pavimenta en producto.

Qué significa en la práctica

RasgoQué implica
La ambigüedad es el defaultNo vas a recibir requerimientos claros. Los descubrís construyendo, adentro.
Alta agenciaEs el primer rasgo que pide Anthropic para el puesto, antes que cualquier requisito técnico.
Rango en un mismo díaDebuggear con el equipo técnico a la mañana, explicar un tradeoff de alcance a un director a la tarde.
Velocidad, con deuda como monedaSe entrega en semanas. Generalizar es otra etapa.
La métrica no son horasEs cuánto de lo que construiste volvió al Canon. Utilización alta es alarma, no logro.
Las dos trampas

Si el trabajo a medida no se convierte sistemáticamente en algo reutilizable, esto es consultoría con otro nombre.

Por debajo de cinco cifras bajas, la matemática no cierra. Ver §6.

08El programa

Tres etapas, sin fechas

Cada una cierra con un artefacto real y un gate. El eje es deployá y aprendé lo que te falta para deployar, no estudiá y después deployá.

Primeras tareas reales — nada inventado

  • README.md, canon/README.md y WF_CANON_DEPLOY.md describen las instancias como subdirectorios clients/<name>/; el Mark IV §5 ya las movió a repos standalone.
  • El skill upc está en .claude/skills/ pero falta en capabilities/skills/REGISTRY.md.
  • TL_CORE_MCP sigue marcado "Pending inventory" mientras el runtime ya corre Notion, Figma y Excalidraw.
Gate 1

Tu instancia bootea (CLAUDE.md → spec → pulse resuelve) · al menos un AG_, un WF_ y un TL_ propios funcionando · una Connection autenticada con op · una rutina de cadencia · una tarea de deuda cerrada. Al pasar: acceso de escritura al C-OS de COMANDO.

02

Go-to-market

Entregable: una campaña viva, instrumentada, con pipeline real de conversaciones.

No se rehace lo que existe: comando-ai.com, el AI Readiness Test como lead magnet, el deck de pitch, el Canon como método. El playbook técnico ya está investigado — Stripe, Meta y Google Ads por MCP, GA4, Notion como CRM, y qué se automatiza contra qué se gatea. Trabajás bajo AG_MKT_CMO, AG_MKT_GROWTH y AG_MKT_CONTENT.

Primera tarea acotada: cerrar la captura de leads del readiness test. El test está vivo, pero el mail y el CRM skipean en silencio — hoy no se guarda ni un lead. Chico, verificable, y te obliga a tocar DNS, variables de entorno, Resend y Notion.

Gate 2

Campaña viva · leads que efectivamente aterrizan en el CRM · registro honesto de qué funcionó y qué no en cadence/decision_log.md.

03

Cliente real

Entregable: un engagement corrido de punta a punta, con vos como FDE, más un output de Layer A.

El cliente es el que trajiste vos en la etapa 2. Corrés WF_CANON_DEPLOY completo. El principal acompaña; vos conducís.

El acceso a los datos del cliente es el camino crítico, y es donde mueren los proyectos — ocho a doce semanas peleando por acceso y la última semana corriendo para tener algo que mostrar. Se arranca el día cero.

En paralelo, research: un proyecto de Layer A con el skill researcher. Esto es lo que hace que sea un lab y no una consultora.

Gate 3

La instancia del cliente bootea y pasa canon-lint · una research registrada · una propuesta escrita tuya sobre qué de este engagement debería volver al Canon. Ese último punto es el gate de verdad.
